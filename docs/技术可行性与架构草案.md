# 技术可行性与架构草案

版本：0.2  
日期：2026-08-13

## 总结

目标功能在当前 Apple M5 MacBook Air 与 macOS 26.5.2 上均有可行路线。为了同时实现 GPU 三项利用率、摄氏温度和 AirPods 左右耳/充电盒状态，首版定位为自行安装的 Developer ID 非沙盒应用，不以 Mac App Store 为目标；用户已确认接受这一形态。

应用采用 SwiftUI + 少量 AppKit/系统框架，使用 `MenuBarExtra` 的窗口样式构建菜单栏弹出面板，并通过 `LSUIElement=true` 隐藏 Dock 与应用切换器图标。

## 数据来源

### CPU

- 使用公开的 Mach `host_statistics(HOST_CPU_LOAD_INFO)`。
- 对两次累计 tick 做差，分别计算用户（USER + NICE）、系统和空闲百分比。
- 第一次采样只建立基线；面板打开时每秒采样一次。
- 不运行 `top`、`ps` 或其他子进程。

稳定性：高；无需权限；开销很低。

### GPU

- 使用 IOKit 在进程内匹配 `IOAccelerator` 服务。
- 从 M5 的 AGX 驱动 `PerformanceStatistics` 读取：
  - Device Utilization
  - Renderer Utilization
  - Tiler Utilization
- 缓存 IOService 句柄，每秒只读取一次属性，不反复运行 `ioreg`。
- Renderer 和 Tiler 是独立指标，不把它们设计成总和必须为 100% 的堆叠数据。

稳定性：中；IOKit 调用公开，但 AGX 属性名称没有公开稳定契约。键缺失或系统升级不兼容时显示“暂不可用”。

### 温度

- Apple 的公开 API 只能提供 `ProcessInfo.thermalState` 热状态等级，不能提供摄氏度。
- M5 上公开的 `PROCESSOR_TEMPERATURE` 调用实测不可用。
- 数值温度首版计划通过动态枚举 Apple Silicon IOHID PMU die 传感器获得。
- 显示有效芯片 die 传感器中的平滑最高值，名称必须是“芯片最高温度”，不冒充精确的“CPU 温度”。
- 私有数值读取失败时，退化为“正常／轻微／严重／危急”等系统热状态。

稳定性：数值温度为中低，属于私有 SPI；热状态回退为高。无需 root helper。

### AirPods Pro

- 使用公开 IOBluetooth 获取已配对设备、连接状态，以及连接/断开事件。
- 电量与充电快照按需执行系统自带的 `/usr/bin/pmset -g accps -xml`，解析 plist，而不是解析本地化文本。
- 目标字段包括分组标识、部件标识、左右耳/充电盒、当前容量与充电状态。
- 面板打开时立即刷新；打开期间最多每 30 秒校验一次；面板关闭后完全停止定时查询，只保留蓝牙连接事件。
- 不持续进行 CoreBluetooth 扫描，不把蓝牙偏好缓存当作主数据源，也不频繁运行 `system_profiler`。
- 当前 AirPods 尚未到手，必须连接实物后按状态矩阵校准具体字段。

稳定性：连接状态高；三部件电量中。`pmset accps -xml` 是轻量系统兼容层，但不是 Apple 明示的稳定公开接口。

### Codex 剩余用量

- 使用官方 Codex App Server 的 `account/rateLimits/read`。
- 通过 Swift `Process` 与 stdio JSONL 依次完成：
  1. `initialize`
  2. `initialized`
  3. `account/read`
  4. `account/rateLimits/read`
- 从 `usedPercent`、`windowDurationMins` 与 `resetsAt` 计算剩余百分比、窗口类型和重置时间。
- 按窗口时长识别 5 小时、一周或未来新增额度；不硬编码 primary/secondary 的含义。
- 复用本机 Codex 的 ChatGPT managed 登录状态，但不读取或复制 `auth.json`、JWT、邮箱或其他凭据。
- 面板打开且缓存超过 30–60 秒时，短暂启动 App Server；查询完成立即退出。没有后台额度轮询。

稳定性：高，属于官方接口；需要允许官方进程正常访问自己的 `~/.codex` 状态与刷新登录信息，因此不适合 App Sandbox。

### 开机运行时长

- 使用系统 boot time/uptime 数据计算本次开机后已运行时间。
- UI 根据本地时间经过量更新，不需要高频系统查询。

稳定性：高；无需权限。

### 登录后自动启动

- 使用系统 ServiceManagement 的 `SMAppService.mainApp` 注册或取消主应用登录项。
- 不手工写入 LaunchAgent plist。

稳定性：高；由用户在系统登录项权限中控制。

## UI 架构

- 使用原生 SwiftUI `MenuBarExtra`，采用 `.window` 弹出式窗口样式。
- `LSUIElement=true`，应用不显示在 Dock 或应用切换器中。
- macOS 26 采用系统原生 Liquid Glass；标准控件优先使用系统自带外观。
- 自定义玻璃卡片集中在少量容器中，避免为每一层重复叠加实时模糊。
- 菜单栏使用单色模板图：球衣轮廓 + `10`，自动适配深浅菜单栏。

## 低功耗生命周期

### 面板关闭

- CPU/GPU/温度采样定时器不存在。
- CPU/GPU 历史数组不更新。
- 不运行 Codex App Server、`pmset`、`ioreg`、`system_profiler` 或其他周期子进程。
- 仅保留菜单栏 App、本地状态，以及轻量的蓝牙连接事件。

### 面板打开

- 使用一个统一、可容忍延迟的 1 Hz 采样节拍读取 CPU、GPU、温度与更新图表。
- 图表使用固定容量环形缓冲区，仅保留最近 60 个采样点。
- AirPods 立即读取，随后最多每 30 秒校验。
- Codex 只在缓存过期时读取一次；重置倒计时由本地 `resetsAt` 计算。

### 睡眠与唤醒

- 睡眠时停止全部采样。
- 唤醒后重新建立 CPU 基线、重新匹配可能失效的 GPU/温度服务，并刷新连接状态。

## 禁用方案

- 不使用要求 root 的 `powermetrics` 作为应用数据源。
- 不每秒运行 `ioreg`、`top`、`system_profiler` 等外部命令。
- 不持续执行 CoreBluetooth 扫描。
- 不通过辅助功能点击、OCR 或截图读取 Codex UI。
- 不直接读取、解析或复制 Codex 登录令牌。
- 不为了后台“保持新鲜”而常驻 Codex App Server。

## 必须实机验收的风险

1. IOHID 数值温度在最终签名构建中的可读取性及传感器语义。
2. AGX GPU 私有属性在 macOS 26.5.2 上的数值正确性和升级退化行为。
3. AirPods Pro 到手后，左右耳、充电盒、充电状态在所有连接/盒盖状态下的字段映射。
4. Codex App Server 查询结果与左下角 UI 的百分比及重置日期一致。
5. 面板关闭数小时后的 CPU、唤醒次数、内存与能耗影响。
